# 实验 0：一条命令的生命周期

## 0. 实验概述与核心概念

本实验不编写代码。任务目标是运行 xv6 系统并追踪 `echo hi` 命令从键盘输入、系统调用、程序装载到终端回显的全生命周期，最终交付三张系统图纸：系统控制流图、核心数据结构快照、时钟中断与上下文切换时序图。

### 核心概念索引

| 概念 | 说明 | 重点探究方向 |
| --- | --- | --- |
| **U 态 / S 态** | U 态为受限用户模式；S 态为特权内核模式，负责管理硬件外设、内存与中断。 | 特权级切换时机与硬件保护机制 |
| **系统调用** | 用户程序通过 `ecall` 指令陷入内核态，请求内核执行特权操作。 | 参数传递规范与返回值约定 |
| **用户栈 / 内核栈** | 进程在用户态使用用户栈；陷入内核后切换至当前进程专属内核栈。 | 栈空间切换时机与上下文隔离 |
| **陷入帧（trapframe）** | 陷入内核时用于保存 31 个用户态通用寄存器现场的内存结构。 | 寄存器保存与恢复时机 |
| **跳板页（trampoline）** | 包含特权级切换与页表切换汇编指令的专用物理页面。 | 双重页表映射原因（见思考题 1） |
| **页表项（PTE）** | 虚拟地址转换映射单元，包含物理页号及权限标志位（V、R、W、X、U）。 | 地址空间各区域权限配置规则 |

硬件实际提供三层特权级。除 U 态与 S 态外，还有 **M 态（Machine Mode）**，这是 CPU 复位后的最高特权级，仅在上电初始化阶段使用（见实验 1）。xv6 日常运行只涉及 S 态与 U 态。在本课程中，“内核态”指 S 态，“用户态”指 U 态。特权级转换时，硬件会自动保存关键状态，例如 `sstatus.SPP` 记录陷入前的特权级，`sret` 依据该位决定返回 U 态还是 S 态。

### 常用 CSR 命名速查（s- 前缀 = S 态，m- 前缀 = M 态）

阅读源码注释与 RISC-V 规范时常见的控制状态寄存器（CSR）缩写与全称对照如下：

| 缩写 | 全称 | 作用 |
| --- | --- | --- |
| `scause` | supervisor cause | 本次陷入的原因编号；最高位为 1 表示异步中断 |
| `sepc` | supervisor exception program counter | 陷入瞬间的断点 PC，`sret` 返回时使用 |
| `stvec` | supervisor trap vector | 陷入入口地址，指向 `uservec` |
| `stval` | supervisor trap value | 出错时的地址或指令内容 |
| `sscratch` | supervisor scratch | 陷入瞬间的内核暂存寄存器（本实验内核用它保存 `trapframe` 地址） |
| `satp` | supervisor address translation and protection | 当前页表基址与分页模式 |
| `sstatus.SPP` | previous privilege | 陷入前所在的特权级，`sret` 据此决定返回 U 态还是 S 态 |
| `sstatus.SPIE` | previous interrupt enable | 陷入前的中断使能状态 |

带有 `m-` 前缀的寄存器（如 `mepc`、`mtvec`、`mstatus`）属于 M 态，将在实验 1 中使用。

### 本树函数命名对照（与旧版 xv6 及网上资料）

本课程实验基线基于新版上游代码，部分内核函数名称与旧版教材或网络资料不同。用户态系统调用接口（`fork`、`exec`、`exit`、`wait`）保持不变，变更的仅是内核内部实现函数：

| 本树命名 | 旧版 xv6 / 网上资料 | 用途 |
| --- | --- | --- |
| `kfork` | `fork` | 创建子进程 |
| `kexec` | `exec` | 装载新程序 |
| `kexit` | `exit` | 进程退出 |
| `kwait` | `wait` | 等待子进程 |
| `prepare_return` | `usertrapret` | 返回用户态前的准备 |
| `uartwrite` | `uartputc` | 串口批量输出（同步版仍名 `uartputc_sync`） |
| `sleep_prepare ＋ sleep`（两段式） | `sleep(chan, lock)`（一段式） | 休眠拆分为登记等待与让出 CPU 两步 |

`usertrap`、`uservec`、`userret`、`devintr`、`consoleread`、`consolewrite`、`uartintr`、`swtch`、`uvmcopy`、`yield`、`scheduler`、`wakeup` 等多数名称保持一致。

### 任务一：绘制 `echo hi` 系统控制流图

**任务目标**：梳理从用户按下回车键到终端输出下一个提示符 `$` 期间，CPU 上执行的完整事件流，按时序绘制函数调用、系统调用、中断响应及进程状态流转图。

**阅读建议**：首先阅读 `user/sh.c` 中的 `main` 循环及命令解析、子进程创建与装载逻辑；然后进入内核源码，逐项追踪系统调用的内核执行路径。

#### 阶段 1：Shell 输入与等待

> - 参考源码：`user/sh.c`、`kernel/sysfile.c`（`sys_read`）、`kernel/console.c`（`consoleread`）。
> - 确认 Shell 获取输入字符所调用的系统调用及其参数定义。
> - 分析未输入完整命令时 Shell 进程的状态（`state`）及等待机制（轮询或阻塞挂起）。
> - 梳理按下回车后唤醒 Shell 的外部中断触发路径及内核中断处理函数（`kernel/trap.c` 与串口驱动）。

#### 阶段 2：创建子进程（`fork`）

> - 参考源码：`kernel/proc.c`（`kfork`、`uvmcopy`）。
> - 梳理 `fork` 分配的资源、复制的页表及子进程初始状态。
> - 分析 `fork` 在父进程与子进程中的不同返回值及其硬件传递机制（见思考题 2）。
> - 确认子进程开始执行的具体代码入口。

#### 阶段 3：装载程序（`exec`）

> - 参考源码：`kernel/exec.c`（`kexec`）、`kernel/sysfile.c`（`sys_exec`）。
> - 分析子进程调用 `exec` 后地址空间的变化及原程序镜像的释放过程。
> - 确认内核从 ELF 格式文件中读取的代码段、数据段在物理内存中的载入位置。
> - 分析命令行参数（`argc`、`argv`）在用户栈中的布局方式。

#### 阶段 4：执行程序与控制台输出

> - 参考源码：`user/echo.c`、`kernel/sysfile.c`（`sys_write`）、`kernel/console.c`（`consolewrite`）。
> - 确认 `echo` 输出字符串调用的系统调用及内核处理函数链路。
> - 确认字符最终写入的外设硬件接口，并对比控制台输入与输出在内核实现上的异同。

#### 阶段 5：进程退出与资源回收

> - 参考源码：`kernel/proc.c`（`kexit`、`kwait`）。
> - 分析 `echo` 调用 `exit` 后进程状态的转变及父进程唤醒机制。
> - 梳理 Shell 在 `wait` 调用中的等待与回收流程，以及重新打印提示符的时机。

#### 标注要求

> - 明确标注每个执行步骤所在的特权级（U 态 / S 态）；
> - 明确标注每个执行步骤所使用的栈空间（用户栈 / 进程内核栈 / 调度器专属栈）；
> - 标注特权级切换的触发原因（`ecall` / 外部中断 / `sret`）；
> - 标注进程在 `read` 与 `wait` 上阻塞挂起后 CPU 切换至调度器执行的转折点。

**验证方法（自检）**：使用 QEMU 的 `-d int` 参数记录运行过程中的陷入事件，核对图纸中的系统调用时序。日志数据量较大且包含大量时钟中断，建议按以下四步进行切片分析：

> 1. **确定时间窗口**：以 Shell 提示符打印后的第一次 `read` 系统调用为起点，下一次 `read` 调用为终点，截取 `echo hi` 命令执行期间的日志。使用 `grep -n 'async:0' int.log` 找到首尾行号，再通过 `sed -n '起点,终点p' int.log > slice.log` 提取切片。
>
> 2. **统计陷入类型**：执行 `grep -o 'cause:[0-9a-f]*' slice.log | sort | uniq -c | sort -rn` 统计各类 `cause` 码出现的次数，按频次分析主要事件。
>
> 3. **过滤干扰项**：时钟中断（`cause:0000000000000005`）发生频率较高，可执行 `grep -v 'cause:0000000000000005' slice.log` 进行过滤。保留的条目主要为系统调用 `ecall`（`cause:0000000000000008`）与外部中断（`cause:0000000000000009`）。注意键盘和磁盘外设共用外部中断号，可结合执行阶段区分：`exec` 装载镜像期间主要为磁盘中断，键盘输入期间主要为串口中断。
>
> 4. **归并与地址翻译**：执行 `grep 'async:0' slice.log | grep -o 'epc:0x[0-9a-f]*' | sort | uniq -c` 提取唯一的 `epc` 地址列表。几十次系统调用通常只对应少数几个固定地址。逐个将地址翻译回源码行：
>
>    - 内核地址（`0x80` 开头）：使用 `riscv64-unknown-elf-addr2line -e kernel/kernel -f 0x地址` 查询。
>    - 用户态地址：先通过 `riscv64-unknown-elf-objdump -d user/_sh | grep -B2 ecall` 查找对应的系统调用桩函数，再使用 `addr2line` 定位源码。

> **⚠️ 警告**
>
> 使用 `addr2line` 查询用户态地址时，必须指定触发该系统调用的目标程序二进制文件。所有用户程序均从虚拟地址 0 开始链接，不同二进制文件中的相同地址对应完全不同的函数。

核对标准：图纸中的每个系统调用节点均应能在切片窗口中找到对应的 `ecall` 记录，且先后顺序一致；若日志中出现图纸未列出的重复地址（如用户态标准库逐字符调用 `write`），可作为典型现象写入图纸批注中。

### 任务二：绘制 `exec` 完成关键时刻的数据结构快照

**切片时机**：`exec("echo", ...)` 装载完成且尚未执行第一条用户指令的瞬间。

**任务目标**：结合源码定义，绘制该时刻的进程表、地址空间与文件描述符表快照。

#### 1. 进程表快照

查阅 `kernel/proc.h` 中的 `struct proc` 定义与 `kernel/proc.c` 中的进程数组，绘制当前系统中关键进程的状态：

> - 梳理当前系统中存在的各进程（`init`、`sh`、`echo` 等）；
> - 确认各进程当前的 `state` 取值，并在源码中找出设置该状态的代码行；
> - 确认 `echo` 进程的 `sz` 字段与 `trapframe->epc` 寄存器保存的具体内容。

#### 2. `echo` 进程虚拟地址空间与页表快照

绘制 `echo` 进程从虚拟地址 `0x0` 到最高虚拟地址 `MAXVA`（定义于 `kernel/riscv.h`）的完整映射关系，未映射区域标记为空洞：

> - 梳理 `kernel/exec.c` 中建立的各段内存映射（代码段、数据段、保护页、用户栈等）；
> - 标注各映射段的页表项权限标志位（V、R、W、X、U），并分析各权限设置的原因；
> - 明确位于地址空间顶部的两个特殊页面（`trampoline` 与 `trapframe`）的映射位置与权限位；
> - 明确用户栈在 xv6 中的位置：紧邻 ELF 程序段（代码/数据）与 Guard Page 之上，而非从高地址 `MAXVA` 向下生长；
> - 分析用户栈下方保护页（Guard Page）的作用及防溢出机制；
> - 说明用户栈顶除常规数据外保存的参数信息。

#### 3. 文件描述符表快照

绘制 `echo` 进程内部的 `ofile` 打开文件数组：

> - 确认文件描述符 `0`、`1`、`2` 分别指向的对象类型（设备/文件）及内核对应结构；
> - 结合 `user/init.c` 与 `fork`、`exec` 的继承规则，梳理这三个文件描述符的初始创建与传递链路。

#### 4. 验证方法（自检）

> - **进程表快照**：在 QEMU 控制台按下 `Ctrl-P`，内核的 `procdump()` 函数会输出各进程的 `pid`、`state`（如 `sleep`、`runble`、`run`、`zombie`）与进程名。可将输出结果与快照中 `init`、`sh` 的状态进行核对。
>
> - **`exec` 瞬间的 `sz` 与 `epc`**：由于 `echo` 执行极快，手动截取状态较为困难，可通过代码插桩获取确切数值。在 `kernel/exec.c` 中设置 `p->trapframe->epc = elf.entry;` 的代码行后添加一行打印：
>
> ```c
> printk("kexec %s: pid=%d sz=0x%lx epc=0x%lx\n",
>        p->name, p->pid, p->sz, p->trapframe->epc);
> ```
>
> 重新执行 `make qemu` 并运行 `echo hi`：输出中的 `sz` 应与快照中绘制的镜像顶端地址一致，`epc` 则对应 `echo` 的入口地址（可与 `_echo` 反汇编中的入口对照）。验证完毕后移除插桩代码。注意本内核打印函数名为 `printk`，支持 `%d`、`%x`、`%lx`、`%p`、`%s` 等格式说明符。
>
> - **页表快照**：静态查阅 `kernel/exec.c` 中的 `uvmalloc`、`loadseg` 与 `copyout` 调用，核对各段对应的权限标志位（V、R、W、X、U）与映射范围。
>
> - **文件描述符快照**：在插桩位置同时打印 `p->ofile[0..2]` 的指针值，结合 `kexit` 与 `fileclose` 的实现，验证标准输入、输出与错误输出是否指向同一个控制台文件结构。

### 任务三：追踪时钟中断与上下文切换时序

**任务目标**：深入追踪用户进程在执行期间被时钟中断抢占并让出 CPU，随后经调度器重新恢复执行的完整闭环，绘制时序流转图。

#### 步骤 1：硬件响应中断

> - 查阅定时器中断产生时 CPU 硬件自动更新的控制状态寄存器；
> - 确认时钟中断对应的 `scause` 寄存器取值及其最高位的含义；
> - 分析内核区分外部中断与同步异常的判断逻辑。

#### 步骤 2：保存现场（`kernel/trampoline.S`）

> - 分析中断触发后 CPU 首先进入 `uservec` 汇编代码而非 C 处理函数的原因，确认 `stvec` 寄存器的配置位置；
> - 梳理 `uservec` 利用 `sscratch` 寄存器获取 `trapframe` 地址的过程；
> - 梳理从 `uservec` 保存通用寄存器、切换页表与栈指针，直到跳转进入 `usertrap()` 的完整执行序列。

#### 步骤 3：内核处理与让出 CPU（`kernel/trap.c`、`kernel/proc.c`）

> - 分析 `usertrap()` 识别时钟中断的条件；
> - 确认进程触发让出 CPU（`yield`）的判断条件；
> - 追踪进程状态从运行变为就绪的过程；
> - 对比 `swtch` 保存的寄存器子集与 `trapframe` 保存内容的区别，分析被调用者保存寄存器（Callee-saved Registers）在此处的简化原因。

#### 步骤 4：调度器执行中转

> - 确认 `swtch` 切换的目标栈归属（CPU 专属调度器栈）；
> - 确认调度循环所在的内核函数（`scheduler`）及重新选中该进程的条件。

#### 步骤 5：恢复现场与返回用户态

> - 追踪该进程重新被调度后返回用户态原中断指令的执行路径；
> - 分析 `prepare_return`（旧资料名 `usertrapret`）与 `userret` 的执行职责与特权级准备工作；
> - 确认 `sret` 指令完成的特权级切换与程序计数器恢复动作。

#### 标注要求

> - 完整展现时序闭环（用户态中断点 → 内核陷入 → 调度器中转 → 内核返回 → 用户态断点）；
> - 标明各阶段执行所使用的栈空间；
> - 标明 `trapframe` 与进程内核上下文（`context`）各自生效的具体节点。

**验证方法（自检）**：任务三的验证可分为两个层面：

> - **时钟中断触发证据**：在 `-d int` 日志中查找 `scause=0x8000000000000005` 的记录，观察其 `epc` 在用户态地址与内核态地址（`0x80` 开头）之间交替出现，以此验证中断对程序执行的打断。
>
> - **上下文切换与调度过程**：`swtch` 函数保存与恢复 14 个寄存器以及向调度器栈切换属于纯软件执行逻辑，不触发硬件陷入，因此无法通过 `-d int` 观察。可使用临时代码插桩进行验证：
>
>   - 在 `kernel/proc.c` 的 `yield()` 函数中，`p->state = RUNNABLE;` 语句之后添加：
>
>   ```c
>   printk("yield: pid %d -> RUNNABLE\n", p->pid);
>   ```
>
>   - 在 `kernel/proc.c` 的 `scheduler()` 循环中，`p->state = RUNNING;` 语句之后添加：
>
>   ```c
>   printk("sched: pick pid %d\n", p->pid);
>   ```

运行计算密集型程序（如持续创建子进程的测试程序），观察日志中 `yield` 与 `sched: pick` 的交替出现，验证进程从让出 CPU、进入调度循环到被重新选中的完整流转。注意 `echo hi` 执行时间极短，通常不会触发时钟中断让出，因此不宜作为此项验证的测试用例。测试完成后移除插桩代码。

## 3. 思考题

结合源码思考以下问题，并将分析结论以两至三句话的批注形式标注在对应图纸的关联位置：

1. **跳板页（trampoline）双重映射机制**

   跳板页代码同时存在于用户页表与内核页表中，且保持相同的虚拟地址映射。分析这一设计的必要性，并说明若未在两端保持相同虚拟地址，切换页表指令在执行下一条指令时会引发什么问题（批注于任务一或任务二图纸）。

2. **`fork` 调用的双重返回值机制**

   `fork` 仅发起单次系统调用，但父子进程分别获取不同的返回值。在 `kernel/proc.c` 的 `kfork` 实现中定位产生返回值差异的代码行，结合 RISC-V 架构下函数返回值的寄存器传递规范阐明其机理（批注于任务一 `fork` 节点）。

3. **独立调度器栈的设计原因**

   进程切换由 CPU 专属的调度器栈承载，而非直接运行于某一个进程的内核栈上。结合 `exit` 退出回收流程，分析若调度器直接在正在退出的进程内核栈上运行会导致什么后果（批注于任务三图纸）。
